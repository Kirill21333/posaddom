# ПосадДом: информационная система управляющей компании

Рабочая реализация курсового проекта «Автоматизация приёма и контроля заявок на техническое обслуживание МКД» для ООО УК «Посадское обслуживание домов»: регистрация заявок с автоматической нумерацией и расчётом сроков, автоназначение исполнителей по специализации, графику и нагрузке, контроль сроков (предупреждения и просрочки), фотофиксация, начисления по платным услугам, уведомления и очередь обмена с внешними системами (ГИС ЖКХ, РСО, SMS, почта), справочники, отчёты и администрирование. Интерфейс сделан по макетам Figma (`design/*.png`), требования - в `SPEC.md` и разделе 7 курсовой.

## Стек

* Frontend: HTML5, CSS3, нативный JavaScript (ES-модули, SPA с hash-маршрутизацией, без сборки и зависимостей).
* Backend: PHP 8.2 без фреймворка (собственный роутер, слои «контроллеры -> сервисы -> PDO»), JSON REST API.
* БД: MariaDB 10.4+ / MySQL 8 (`posaddom`, 35 таблиц, 4 представления, триггеры целостности), utf8mb4.
* Внешние сервисы заменены заглушками: письма пишутся в `storage/mails`, SMS - в `storage/sms`, обмен с ГИС ЖКХ и РСО идёт через очередь `integration_queue` (журнал `storage/logs/integration_*.log`). Composer не нужен.

## Быстрый старт (Windows + XAMPP)

```bat
start.bat
```

Скрипт запускает MariaDB из XAMPP, создаёт базу `posaddom` с демо-данными (если её ещё нет) и поднимает веб-сервер на **http://127.0.0.1:8300** (порт 8080 не используется).

Вручную:

```bash
php -d extension=gd database/install.php --demo      # --force пересоздаёт базу; без --demo создаётся только администратор
php -S 127.0.0.1:8300 -t public public/index.php
```

Расширение `gd` нужно только для генерации фото-заглушек в демо (если оно не подключено, заглушки создаются в PNG без GD). Подключение к БД: `127.0.0.1:3306`, пользователь `root` без пароля; переопределения - в `config/config.local.php` (массив, сливается с `config/config.php`).

## Основные правила (кратко; подробно - SPEC.md и ТЗ 7.6)

* **Номер заявки** `<А|С|П>-<год>-<6 цифр>`: счётчик года в `request_number_seq`, выдача в транзакции `SELECT ... FOR UPDATE`, нумерация сквозная; UNIQUE на `request_number`.
* **Сроки**: аварийная 30 мин / 24 ч, срочная 2 ч / 72 ч (календарно); плановая - выезд «в то же время следующего рабочего дня» (пн-пт 09:00-18:00; время вне рабочего дня приводится к его границе), устранение 168 ч; `warn_at = received + 0,75 * (due - received)` (по `settings.warn_percent`). Сроки - снимок в заявке, пересчитываются только при смене категории.
* **Автоназначение**: активные исполнители с нужной услугой и привязкой к дому, в смене (график + исключения); для аварийных допускается вне смены (`off_schedule`, уведомление «вызов вне графика»). Нагрузка = сумма весов открытых заявок (назначена / выполняется). Выбирается минимальная нагрузка, при равенстве - тот, кому назначали раньше всех; предел `max_load` берётся из правила с наименьшим `priority` (иначе `settings.default_max_load`). Нет кандидатов - `manual_assign_required = 1`, заявка в очереди, уведомление диспетчерам.
* **Статусы**: new -> accepted -> assigned -> in_progress -> done -> closed; new/accepted -> rejected; new/accepted/assigned/in_progress -> cancelled. Закрыть можно только `done` при наличии фото «после»; после закрытия правка запрещена (и триггером БД), допустим только комментарий `is_additional_contact = 1`. Платная услуга при закрытии даёт начисление.
* **Фото**: JPEG/PNG до `settings.photo_max_mb` МБ, тип проверяется по содержимому; `retention_until = дата + 3 года`, удаление раньше срока запрещено (API и триггер).
* **Фоновые задания** (`php cron/run.php [check_deadlines|process_queue|cleanup|backup|all]`): предупреждения по 25 % срока, отметка просрочки, повтор очереди интеграций, очистка просроченных фото. Без планировщика (`app.lazy_cron = true`) задания запускаются из запросов раз в 5 минут.
* **Интеграции**: ГИС ЖКХ, РСО, SMS, e-mail, мессенджер - через `integration_queue` (до 5 попыток, повтор через 5, 10, 15... минут; статусы pending / sent / error). `settings.integrations_enabled = 0` имитирует недоступность внешних систем: основная работа не блокируется, сообщения копятся в очереди.

## API

Префикс `/api`, JSON, сессионная cookie `PDSESS`. Успех: `{"ok":true,"data":...}`; ошибка: `{"ok":false,"error":"текст на русском","code":"...","fields":{...}}` с HTTP-статусом 400/401/403/404/409/422. Полный контракт - в `SPEC.md`. Эта часть: `/auth/*`, `/ref`, `/requests*`, `/photos/{id}`. Маршруты справочников, отчётов и администрирования подключаются из `src/routes_extra.php` (файл возвращает функцию `function (Router $r): void`).

Служебные детали ядра:

* `POST /requests` и `POST /requests/preview` принимают необязательное `received_at` (ГГГГ-ММ-ДД ЧЧ:ММ:СС, не в будущем и не старше 30 суток): диспетчер регистрирует обращение задним числом, сроки считаются от него.
* 409 при дубле клиента: `{"ok":false,"error":...,"duplicate":{...},"data":{"duplicate":{...}}}` (дополнительные ключи ответа задаются через `HttpException::with()`).
* `GET /requests`: `counts` считаются в пределах видимости пользователя без учёта фильтров: `new` = статусы new + accepted, `queue` = очередь нераспределённых, `in_work` = assigned + in_progress, `overdue` = открытые с истёкшим сроком, `closed` = статус closed.
* `GET /requests?status=`: один код или список через запятую (`status=new,accepted`, `status=assigned,in_progress`) - так вкладки «Новые» и «В работе» совпадают с `counts.new` и `counts.in_work`; неизвестный код - 422.
* `GET /requests/{id}/candidates`: все активные исполнители с признаками `on_schedule`, `matches` (услуга и дом), `within_limit`, `load` / `max_load` и флагом `recommended`.
* `GET /auth/me` у неавторизованного возвращает 401; `POST /auth/login` при блокировке - 403 с `code: "locked"`.
* `DELETE /photos/{id}` (администратор): только после окончания срока хранения и закрытия заявки.

## Тесты

```bat
tests\run_all.bat
```

Пересоздаёт БД с демо-данными и запускает `unit_test.php` (DeadlineService, NumberingService, AssignmentService без HTTP) и `api_test.py` (ТК-01...ТК-18 через HTTP; фикстуры создаются самим тестом, поэтому результат не зависит от времени суток). Проверки справочников, отчётов и администрирования получают статус SKIP, если эндпоинт не отвечает.

## Допущения и отступления от SPEC

* Схема совпадает с `model.py` (35 таблиц, 52 FK); сверх модели добавлены только индексы, уникальные ключи (`work_schedules` по (сотрудник, день недели), `schedule_exceptions` по (сотрудник, дата), `premises` по (дом, номер)) и CHECK (`weekday` 1-7, `due_at >= received_at`, для категорий задан выезд в минутах или рабочих днях).
* Предельная нагрузка проверяется как `L + вес новой заявки <= max_load` (нагрузка после назначения не превышает предел).
* Перерывы в графике на автоназначение не влияют; `calendar_time` категории не используется (устранение всегда календарное, как в ТЗ).
* Защита от CSRF: cookie `SameSite=Lax` и проверка заголовка `Origin` у изменяющих запросов (токен не требуется).
* Сотруднику без e-mail уведомление дублируется в «мессенджер» (файл в `storage/mails`), остальным - письмом.
* Заявка из очереди, поступившая из ГИС ЖКХ, остаётся в статусе «Новая» до принятия диспетчером (как на макете); для остальных после регистрации - «Принята в работу» либо «Назначен исполнитель».
* Резервная копия в `cron/run.php backup` делегируется `App\Services\BackupService::create()` (раздел администрирования).
